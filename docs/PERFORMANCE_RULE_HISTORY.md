## 人工操作

使用 `python tools/performance_review.py --db data/demo-ui.db pending` 查看未关联消息与待核验单元。用 `list` 查看台账，`audit` 查看修改历史。

写操作使用本地 JSON 文件，例如：

```json
{
  "action": "revise",
  "arguments": {
    "unit_id": "实际计量单元ID",
    "actor": "实际核验人",
    "reason": "补充证据，原计量需重新核验",
    "evidence": "实际证据位置或记录ID",
    "status": "PENDING"
  }
}
```

执行 `python tools/performance_review.py --db data/demo-ui.db apply --input review.json`。不要将示例人员或证据写入真实台账。支持建立计量单元、关联消息、记录原始时间和发送证据、折算申请/核准、确认、合并、拆分、撤销、异常核验与时效评估；均仅修改本地台账，不发送消息。

`flag_anomaly` 只创建疑似异常；`review_anomaly` 需要实际核验人、依据和原因。事件数与涉及单元数分别保留，未确认分子分母不产生异常率，更不会自动计算月度处罚或工资系数。

`timing` 保存完整输入和结果：原始时长、调整后时长、时效状态。政策中的带时区日期区间可表达工作日、周末、寒暑假、指定节假日的真实排班；必须提供确认记录及覆盖期间。用餐排除须有核准证据，重叠区间只扣除一次。高峰需分别提供“至少两道完成”与“全部完成”时点、截止时刻和证据；夜间遗留截止时间单独配置。未配置时返回待核验，不使用统一60分钟冒充已核准时效规则。

金额估算使用独立 `estimate` 操作。必须明确 `confirmed`、`evidence`、`tier_method`（`progressive` 或 `whole_tier`）；听力语法需确认 `listening_grammar_additive`，夜间需 `night_price_unit="篇"` 和明确 `night_price`。结果始终为“暂估”，不会自动成为“已核定薪酬”。
